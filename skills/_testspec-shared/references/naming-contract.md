# 命名契约（test-points ↔ testcase-generate 共享）

> 目标：建立一套长期稳定、可判定的命名规则，使 points 的"要测什么"和 generate 的"怎么测"在前两段（模块/功能点）严格对齐，第三段分别表达验证意图/测试场景。

## 权威来源（模块/功能点）

- `{模块}`、`{功能点}`只能来自 testpoints.md 的标题层级：
  - `### {模块}模块`
  - `#### {功能点}功能`
- 禁止使用同义词/缩写/替换词；后续所有 TP/用例标题前两段必须与标题层级 **严格一致**。

## 命名字典（用于 TP_ID 缩写映射）

`specs/testpoints.md` 顶部必须包含「命名字典」，将中文标题层级映射为 `TP_ID` 所需缩写。这里长期稳定复用的是 `MODULE` / `FEATURE` 缩写，不是完整 `TP_ID`；`TP_ID` 的 SEQ 仍按每次变更独立分配：

- 模块字典：`模块名称 → MODULE`
- 功能点字典：`模块名称 + 功能点名称 → FEATURE`

约束：
- `MODULE` 只允许 `A-Z`，长度 2-5
- `FEATURE` 只允许 `A-Z`，长度 2-10

示例：

```markdown
## 命名字典

### 模块字典
| 模块名称 | MODULE |
|---|---|
| 登录 | LOGIN |

### 功能点字典
| 模块名称 | 功能点名称 | FEATURE |
|---|---|---|
| 登录 | 凭据验证 | CRED |
```

## 测试点名称（TP 标题）

- 格式强制：`{模块}_{功能点}_{验证意图}`
- 仅允许 3 段（即只出现 2 个 `_`）；不得额外分段
- `{模块}`、`{功能点}`必须与当前标题层级完全一致
- `{验证意图}`保持"验证什么（What）"粒度：
  - 禁止步骤词（点击/输入/跳转/选择/上传…）
  - 禁止具体测试数据（如具体手机号/邮箱/固定数值阈值等）
  - 禁止字段名样式（snake_case/camelCase，如 `user_id`、`userId`）
  - 禁止实现方式（Redis/MQ/数据库/表结构/索引…）

## 用例标题（generate 映射规则）

- 格式强制：`{模块}_{功能点}_{测试场景}`（同样只允许 3 段）
- `{模块}`、`{功能点}`必须与 points 标题层级严格一致
- 一个 TP 可映射多个用例：同一 TP 派生的所有用例标题共享相同前缀 `{模块}_{功能点}_...`
- XMind 导出的用例节点只显示 `{测试场景}`，模块与功能点保留在父节点；JSON `test_name`、追溯及命名校验不变。导出时剥离与父节点精确匹配的 `{模块}_{功能点}_` 前缀；三段式名称前缀不匹配时拒绝导出。
- `{测试场景}`允许轻量场景词（正确/错误/边界/异常/权限不足/网络超时等），但避免具体数据
- `module` 字段必须等于 `{模块}`，`submodule` 对应 `{功能点}`；`feature` 作为兼容别名必须等于 `{模块}`。

### 场景名称：简短、直白、见名知意

- 用一句短句写清本用例测什么。优先采用“对象/动作 + 关键结果”或“必要条件 + 动作/结果”，不机械填满所有要素。
- 使用需求中的业务用语；保留区分用例的关键条件，如角色、状态、边界方向、首次/重复。删去后会混淆场景的信息必须保留，不设硬性字数上限。
- 删除“验证……功能是否正常”“测试……场景”“系统能够正确地”等套话；不得只写“正常场景”“异常测试”“操作成功”。
- 名称只表达一个主要意图，不堆叠操作流程、环境背景、多项预期或方法名。详细数据、步骤、判定标准放入对应字段；名称不得新增需求未确认的结果。
- XMind 场景名称不重复父节点分类；保留理解场景所需的业务对象。同一模块/功能点下，不同场景的名称须能区分，不用编号掩盖含糊名称。
- 生成后对照步骤和预期复读名称：读者能否看出测试对象、主要条件或动作、关键结果；是否与实际验证意图一致；是否还能删去不影响理解的词。

以下仅示范名称表达，业务结果须有已确认需求依据：

| 冗长或含糊的场景名 | 简短清楚的场景名 |
|---|---|
| 验证用户输入正确账号密码后能够正常登录系统 | 正确账号密码登录成功 |
| 验证用户输入错误密码时登录功能的处理情况 | 密码错误时拒绝登录 |
| 验证用户没有导出权限时系统的处理情况 | 无权限时禁止导出 |
| 验证重复提交订单的功能是否正常 | 重复提交只生成一条订单 |
| 验证文件大小超过允许上限时上传功能是否正常 | 文件超限时禁止上传 |

## 自检清单（可判定）

生成 testpoints.md 或 testcases.json 后必须自检：

- 文档顶部存在「命名字典」，且覆盖文档中出现的所有 `{模块}`/`{功能点}`
- 每条名称满足：`^[^_\s]+_[^_\s]+_[^_\s]+$` 且前两段严格等于标题层级
- TP 标题/验证要点中不出现步骤词、具体数据、字段名样式、实现关键词；用例场景可写必要的业务动作，但不展开步骤。
- 用例场景符合上述短句规则，与步骤和预期一致，保留关键差异且无套话。语义质量由生成自检和 Review R2 复核，不能仅凭格式校验通过认定名称合格。
