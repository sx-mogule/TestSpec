# TestSpec 思考协议（Thinking Protocol）

> 当前四个公开 Skill 的通用推理框架。每个 Skill 在做决策前，必须走完三个推理阶段，而非用关键词匹配选择策略。

## 目录

- 使用方式
- Phase 1：材料评估
- Phase 2：策略推理
- Phase 3：执行决策
- 工具使用决策
- Phase 4：执行规划
- 适用边界

## 使用方式

在 skill 执行流程的「策略选择」环节，调用本协议。形成执行决策摘要，再进入实际执行；不展示完整内部推理过程。

---

## Phase 1：材料评估

在做任何决策之前，先回答以下 5 个引导问题：

### 1.1 我拿到了什么？

- 列出所有可用输入（proposal.md、requirements.md、requirements-analysis.md、testpoints.md、testcases.json、外部链接、代码仓库等）
- 标注每个输入的存在状态（存在/缺失/部分）

### 1.2 信息密度如何？

- **完整 PRD**：有详细功能描述、交互流程、异常处理、数据规则
- **简短描述**：只有功能名称和简单说明，需要识别缺失规则及其对测试的影响
- **代码仓库/接口文档**：按当前阶段允许范围及来源信任规则核对；技术材料不能自动成为业务事实或 Oracle
- **混合材料**：多种来源，需要交叉验证

### 1.3 有哪些显式信号？

- 用户明确指定的模式、策略、关注点
- 文档中标注的优先级、风险、约束
- 上游 skill 产物中的上下文元数据（参见 context-protocol.md）

### 1.4 有哪些隐式信号？

- 材料中频繁出现的模式（TBD、待定、后续确认 → 完整性风险）
- 业务流程的依赖与并发状态（跨功能交互、重复操作 → 结果可判定性）
- 业务流程的状态转换密度（多状态、多角色 → 逻辑复杂度高）
- 角色权限和敏感业务动作（支付、认证、用户数据 → 功能结果关注）
- 材料中的矛盾或歧义（同一概念不同命名 → 一致性问题）

### 1.5 这些信号对本步骤意味着什么？

- 综合 1.1-1.4 的结果，判断对当前 skill 执行的影响
- 识别信息缺口和风险区域

## Phase 2：策略推理

基于 Phase 1 的评估结果，推导策略组合。不查关键词表，而是通过 3 个核心问题引导推理：

### 2.1 核心问题

根据当前 skill 的职责，回答以下问题：

**对 analysis（需求分析）：**
- "这份材料最大的测试风险在哪里？" → 推导分析模式
- "材料中是否有业务依赖/歧义/矛盾特征？" → 推导补充模式
- "用户的实际关注点是什么？" → 调整模式权重

**对 points（测试点）：**
- "核心业务价值链是什么？" → 决定覆盖深度
- "哪些区域风险最高？" → 决定 p0 分配
- "验证粒度应该多细？" → 控制测试点数量

**对 generate（用例生成）：**
- "用户需要什么粒度的测试？" → 推导测试类型策略
- "哪些场景最容易被遗漏？" → 补充覆盖
- "哪些场景属于最短核心业务闭环？" → 完整集内的冒烟分类

**对 review（用例评审）：**
- "这批用例最可能出什么问题？" → 聚焦检查重点
- "上游分析发现了哪些风险？" → 对风险区域加深检查
- "用例规模和复杂度如何？" → 校准检查深度

### 2.2 策略推导

- 从核心问题的回答中，推导出策略组合
- 分析模式、测试类型策略和设计方法分别从对应数据源选取（`prd-analysis/references/analysis-modes.md`、`testcase-generate/references/test-type-strategies.md`、`test-points/references/test-design-methods.md`）；生成阶段继承 TP 已选方法
- 但选择理由来自推理，而非关键词匹配

## Phase 3：执行决策

输出执行计划摘要，包含以下要素：

### 3.1 决策记录

```
策略选择：<选了什么模式/策略/类型>
选择理由：<基于哪些信号推导出这个选择>
预期规模：<产出的大致规模（问题数/测试点数/用例数）>
风险点：<可能不准确或遗漏的地方>
```

### 3.2 向用户简要说明

用 1-2 句话告知用户：选择了什么策略、为什么这样选择。不需要展示完整推理过程。

## 工具使用决策

在 Phase 1 材料评估中，如果发现信息不足，按以下优先级获取外部信息：

1. **项目规范与需求材料**：适用的 `project-interaction-spec.md`、canonical 需求和直接上游产物
2. **用户提供的来源**：需求文档、链接及已允许的参考证据（获取可访问内容并记录来源）
3. **参考实现证据**：仅在当前阶段与用户允许的范围内核对代码；不得替代已确认需求或把观察结果自动设为 Oracle
4. **公开资料**：仅补充方法或技术事实，不能补造项目业务规则

### 决策原则

- 信息足够时不获取额外信息
- 只获取对当前决策有帮助的信息
- 获取后将关键信息纳入 Phase 1 评估
- 工具使用是可选的，不是必须的
- 阶段边界优先；生成阶段不请求真实 API 探测预期，缺少业务 Oracle 时回到上游澄清

## Phase 4：执行规划（Agentic 决策层）

> 从"推理出策略"升级为"规划完整的执行方案"——Agent 不只决定做什么，还要决定用什么工具、怎么验证、何时求助。

### 4.1 工具与资源选择

基于 Phase 1-3 的结论，决定执行所需的工具链：

- **需要解析文档吗？** 用户提供了 PDF/DOCX → 调用可用解析脚本；纯文本 → 直接读取
- **需要核对参考代码吗？** 仅在阶段和用户允许时定点读取，并保留来源与信任状态，不从实现反推正式需求
- **需要查阅外部文档吗？** 涉及第三方 API、标准规范 → 使用当前环境可用的抓取或搜索能力
- **需要调用校验脚本吗？** 产出 testcases.json 后 → 调用 `validate_testcases.py` 自检

### 4.2 自检策略

产出核心产物后，Agent 自主验证质量：

- **格式校验**（在变更目录中，generate 产出后）：运行共享脚本 `validate_testcases.py --input artifacts/testcases.json --testpoints specs/testpoints.md --pretty`，脚本路径从实际加载的共享目录解析
- **覆盖度检查**：从校验结果的 `coverage` 字段判断是否需要补充用例
- **分布检查**：从校验结果的 `distribution.warnings` 判断比例是否异常
- **修正闭环**：按当前阶段的质量闭环修正并重检；格式错误、覆盖缺口和需求问题分别回到对应责任阶段，未解决不能宣称通过
- **反模式对照**：生成产物后，对照本 skill 的「反模式识别」段落自查

### 4.3 人类介入判断

以下情况**暂停执行，向用户确认**：

- **关键规则缺失**：存在会改变当前执行或 Oracle 的缺口 → 停止相关生成并澄清；材料质量评级本身不决定是否阻塞
- **发现需求矛盾**：同一规则在不同位置定义冲突 → 列出矛盾点请用户澄清
- **阶段规定的修正仍不能解决问题** → 报告具体缺口，不忽略错误或虚构规则继续下游
- **覆盖未达标**：按现有 `coverage.pass` 和完整集至少 95% 的门槛处理；已列 TP 缺用例先在生成阶段补齐，TP 或 Oracle 本身有问题才返回上游。引用覆盖率达标仍须核对所选方法的必要场景

### 4.4 执行计划记录

```
工具链：<需要调用的工具/脚本>
自检计划：<产出后用什么方式验证>
人类介入条件：<在什么情况下暂停>
预期产出：<文件路径和格式>
```

## 适用边界

- 本协议适用于 `prd-analysis`、`test-points`、`testcase-generate`、`testcase-reviewer` 的策略决策环节
- 用户明确指定策略时，跳过 Phase 2 推理，直接进入 Phase 3
- 推理过程应内化，不输出完整推理日志给用户（除非用户要求）
- 推理结果通过 context-protocol.md 传播给下游 skill
- Phase 4 的执行计划是 Agent 内部决策，只向用户输出关键结论（选了什么工具、为什么暂停）
