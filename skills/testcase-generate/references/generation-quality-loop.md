# 用例生成质量闭环

## 确定性门槛

按以下方式解释 `validate_testcases.py` 结果：

- PASS：继续；若有 `review_candidates`，按组交由 Review D5 复核全部成员和实际相似对
- WARN：逐项检查 warning，并修正高影响问题
- FAIL：修复全部错误后重跑
- `coverage.pass=false`：为列出的 TP ID 新增或修复用例

常见修正：

| Finding | 修正 |
|---|---|
| MISSING_FIELD | 补充必需的可执行内容 |
| INVALID_PRIORITY | 按风险使用 p0/p1/p2（小写） |
| DUPLICATE | 只合并真正重复项；否则区分意图 |
| SIMILAR_CASES（复核候选） | 对比条件、数据、边界位置和预期；有必要差异就保留，不凭相似度合并 |
| NAMING_FORMAT | 恢复“模块_功能_场景”标题 |

## 结构复核

- 完整集对全部 TP 的覆盖率至少 95%，并列出所有未覆盖 TP；Smoke 请求不缩小分母。
- Functional/boundary/exception 覆盖必须符合当前证据。
- `type=冒烟` 和 `regression_tier=Smoke` 的用例必须为 p0，类型为冒烟时同步 Smoke 层级；分类仍保留在完整集交付中，不派生独立文件。
- 全 p0 或全 p2 分布触发检查，不能按配额重写。
- 标题模块与 `feature` 一致。

## 判定力自检（反事实）

TP 覆盖率和字段齐全只说明“有用例”，不说明用例能拦住缺陷。逐条回答：**如果实现错了，这条用例会变红吗？**

1. **先定目标缺陷。** 写用例前，从所选方法和已确认规则推出它要拦住的错误实现（见下表），再据此选数据和 Oracle。说不出目标缺陷的用例，多半是重复或仪式感用例。
2. **反事实检验。** 对全部 p0、p1 用例及所有写操作用例，只针对与该用例目标相关的项，假设下列错误实现，判断按当前步骤和预期能否失败：
   - 核心条件被写反，或判定组合漏了一条规则
   - 边界偏移一位（`<` 写成 `<=`，按字节而非字符计数等）
   - 只给出成功提示或页面跳转，业务状态没有变化或没有持久化
   - 拒绝时有提示，但数据已被部分修改
   - 换成相邻状态、角色或 SKU 后结果仍相同
3. **处理。**
   - 应变红而不会变红：补可观察的状态或持久化检查（刷新、重新打开、在列表/详情或另一角色视角核对），或把数据移到真正的边界上。
   - 所需 Oracle 在需求中未定义：不编造，按“修正闭环”退回上游澄清。
   - 与另一用例拦住的缺陷完全相同、且没有独立边界价值：合并或删除。
   - 不为通过自检堆砌与目标无关的断言。
4. **记录。** 在 `_context.oracle_strength` 写检验数量和结果，不在用例字段里写解释：

```json
"oracle_strength": {
  "checked": 18,
  "strengthened": ["<用例 ID>"],
  "merged_or_removed": [],
  "weak_remaining": []
}
```

`weak_remaining` 只放因上游规则未确认而暂时无法加强的用例，并关联对应 Q 编号。Review J2 会反事实抽查本节结论，自检记录不能代替评审。

### 方法与目标缺陷

| 方法 | 典型要拦住的错误实现 | 用例必须体现 |
|---|---|---|
| 等价类 | 某一类输入被并入另一类处理 | 每个必要类别有代表值和能区分的预期 |
| 边界值 | 开闭区间写错、计数口径错（字符/字节/全角） | 端点和相邻值；文本上限同时覆盖键入拦截和粘贴截断 |
| 判定表 / 因果图 | 漏一条规则、条件优先级错 | 每条可行规则的完整动作 |
| 状态迁移 | 非法迁移被允许、迁移后状态未持久化 | 拒绝后状态保持；刷新或重开后状态仍正确 |
| 流程分析 | 取消或返回后残留中间状态 | 每条分支的终态 |
| 错误推断 | 重复提交生成多笔、失败后数据部分写入 | 记录数和关键字段的最终值 |
| 配对组合 / 正交实验 | 两个因子交互时出错 | 每个可行配对至少出现一次 |
| 基于属性 / 变形 / 语法规则 | 只对示例值正确，换一组合法输入就出错 | 不变量或前后关系断言，而不是单点值 |

## 消费者视角复核

在脑中逐条执行用例：

- 对照 `test-design-methods.md` 中所选方法的“完成判断”，核对必要类别、边界、规则、路径、迁移或结果关系是否实际落实到数据、操作及 Oracle。完整 TP 引用覆盖率不代表方法覆盖充分；具体证据留在既有验证要点或 Review J3 中，不往用例字段堆方法解释。
- 场景名称能直接看出主要意图，与步骤、预期一致；不强制把结果补进每个标题。删掉套话和重复背景后，关键条件仍可区分。按共享命名契约改写名称，不能仅凭脚本 PASS 跳过语义复核。
- 四项描述按 `case-design-rules.md` 逐条复读：只保留执行和判定必需的条件、数据、动作与结果，删除套话、重复背景、绕行操作和无关检查。简单场景直接写，不人为增加准备、数据组合或预期数量；必要信息不得为缩短而省略。
- 前置条件直接写必需状态；测试数据只留本例操作和判定必需的字段和值，简短列出，别名与所需对象对应清楚。删去整套配置、无关素材明细和重复背景；精确取值、单位、边界及必要组合保留，无必要数据时留空，不把删掉的冗余内容搬到其他字段。
- 步骤直接写动作和对象，按业务操作阶段组织；连续动作可合成短句，角色切换、等待同步和中间检查不能被合并省略。不依赖另一用例的结果。
- 预期结果直接写可观察、可证伪的状态或变化；同一检查点的关联结果可合写，且能对应相关步骤。
- 不按字数或步骤与预期的数量差判断质量；逐条核对主要目标是否有预期，缺少关键结果时补齐，不写无关内容凑数。
- 用例可重复，且每条只承载一个意图。
- 相似用例不能只是替换名词的模板副本。
- 相似候选须核对数值、单位、空值、角色、状态和边界位置。需求支持的最小合法值、最大合法值和越界值等必要边界即使结果相同也保留；同一等价类中仅换普通数值的用例评估合并。记录复核原因，不用改写标题避开相似度。

## 修正闭环

持续修正到确定性门禁通过；遇到缺失的产品规则时回到上游澄清，不用猜测填补：

1. 只修正明确指出的问题。
2. 重跑确定性校验。
3. 只有校验通过后才重新导出。
4. 在 `_context` 记录迭代次数和修正摘要。
5. 四项描述 finding 修复后重新 Review；由 Review 确认 resolved 并重算描述门禁，生成阶段不得自行清零问题或声明最终通过。

规则改动确需样例挑战时，只复用公共 eval 中 synthetic/non-proprietary 样例；真实历史用例与裁决仅在项目本地回放。原始材料、可判定 Oracle 或可靠裁决缺失时，列明证据缺口，不编造历史样本或声称完成回放。样例挑战不替代完整集 Review。

不得仅为满足指标就忽略 warning、扩大范围或虚构产品规则。

默认校验输出为按组摘要，逐对明细与缓存规则见共享 `execution-efficiency.md`。缓存命中不替代本次业务语义复核；`--no-cache` 可强制重跑，`--full` 可只读输出完整结果。返修只改已定位的问题，完成后仍做完整校验。

## 质量属性

最终用例集必须独立、可重复、可执行、可验证、清晰、完整且单一职责。
