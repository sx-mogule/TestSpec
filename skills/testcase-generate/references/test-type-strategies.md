# TestSpec 测试类型策略单一数据源

> 目标：为 `testcase-generate` 提供稳定的测试类型策略映射。此文件定义”按什么策略展开用例”，不定义最终导出格式。

## 目录

- 使用原则
- smoke / functional / boundary / exception / permission / integration / tracking / compatibility
- 多类型组合规则

## 使用原则（Agentic 选择）

> Agent 不需要使用所有类型。根据已确认的需求选择主流程、边界、异常、角色权限、功能间交互，以及明确要求的埋点或兼容性矩阵场景。

- `testcase-generate` 在推理阶段扫描需求材料，检测每种类型的触发信号
- **有信号** → 纳入本次生成策略
- **无信号** → 跳过，不生成该类型的用例
- 用户指定独立 API、安全、性能等未允许类型时，说明范围限制，不将它们混入允许类型
- 未指定且无明显信号时，默认 `functional`
- 本文件只约束覆盖重点、设计技术和粒度，不改变 `testcases.json`、Excel、XMind 的字段结构

## smoke

- 名称：冒烟测试
- 目标：最小化验证核心主流程是否可用
- 推理触发信号：
  - 用户提到"快速验证""冒烟""基本可用"
  - 材料中有明确的核心业务闭环
  - 上线前紧急测试场景
- 设计策略：
  - 每个核心功能点最多展开 1-2 条用例
  - 优先覆盖最短业务闭环
  - 只保留阻塞性强、失败影响大的场景
- 推荐技术：
  - 主流程场景法
  - 关键节点错误推测
- 输出倾向：
  - 优先生成 `type=冒烟`
  - 必须为 `p0`

## functional

- 名称：功能测试
- 目标：验证功能正确性与主要业务路径
- 推理触发信号：
  - 未指定具体测试类型（默认策略）
  - 用户提到"功能测试""验证功能""完整测试"
  - 新功能上线需要全面验证
- 设计策略：
  - 覆盖有效等价类与关键无效等价类
  - 优先覆盖主路径、核心分支、关键规则
  - 不为追求全面而无限膨胀用例数
- 推荐技术：
  - 等价类划分
  - 场景法
  - 判定表
- 输出倾向：
  - 优先生成 `type=正向`，必要时补充 `负向`

## boundary

- 名称：边界测试
- 目标：验证数值、长度、容量、日期时间等边界条件处理
- 推理触发信号：
  - 材料中有明确的数值范围、长度限制、容量上限
  - 涉及表单输入、文件上传、数据导入等有约束的场景
  - 上游分析标注了边界值相关的风险
- 设计策略：
  - 优先覆盖边界值、边界值±1、空值、满值、典型值
  - 同一验证意图的数据点可以拆成多个独立用例
- 推荐技术：
  - 边界值分析
  - 等价类划分
- 输出倾向：
  - 优先生成 `type=边界`

## exception

- 名称：异常测试
- 目标：验证系统异常处理能力和错误反馈质量
- 推理触发信号：
  - 涉及网络请求、外部服务调用
  - 有支付、数据修改等需要事务一致性的操作
  - 上游分析标注了异常处理缺失的风险
- 设计策略：
  - 覆盖异常输入、重复提交、超时、网络异常、服务异常、并发冲突
  - 关注错误提示、回滚、幂等、数据一致性
- 推荐技术：
  - 错误推测
  - 异常场景法
  - 状态迁移
- 输出倾向：
  - 根据场景落到 `type=负向` 或 `type=异常`

## permission

- 名称：权限测试
- 目标：验证角色访问控制、功能入口暴露和数据隔离
- 推理触发信号：
  - 材料中有角色定义或权限矩阵
  - 涉及多租户、数据隔离
  - 上游分析标注了权限交叉或越权风险
- 设计策略：
  - 明确角色矩阵
  - 同时覆盖有权限、无权限、越权三类场景
  - 优先覆盖高风险操作和敏感数据访问
- 推荐技术：
  - 权限矩阵
  - 场景法
- 输出倾向：
  - 通常落到 `type=负向` 或 `type=异常`

## integration

- 名称：功能间交互
- 目标：验证已确认的跨模块业务动作及用户可观察结果
- 触发信号：需求明确描述前后功能间的状态或数据传递
- 设计策略：分别验证交互前置状态、触发动作及完成后的业务状态；无法直接观察的下游效果标为待确认，不推断完成
- 输出倾向：按业务行为落到 `type=正向` 或 `type=异常`

## tracking

- 名称：埋点测试
- 触发信号：需求明确给出事件触发、事件字段、上报条件或统计口径
- 设计策略：按已确认事件逐项验证触发时机、字段值、条件字段、关联和去重；未定义的时区、去重键等进入澄清，不推断
- 输出倾向：`type=埋点`，引用 Tracking 测试点；预期写出可观察事件或统计结果及需求判定依据

## compatibility

- 名称：兼容性矩阵测试
- 触发信号：需求明确给出平台、系统/浏览器或客户端版本等矩阵维度和对应验收结果
- 设计策略：只展开需求列明的环境组合；每条用例写明环境、同一可复现操作及该环境下可判定结果，不凭常见设备清单补行
- 输出倾向：`type=兼容性矩阵`，引用 Compatibility 测试点

## 多类型组合规则

- `functional + boundary`：主路径及有依据的临界值分别形成独立用例
- `functional + exception`：主路径和关键失败路径分别验证
- `smoke + functional`：冒烟是 p0 核心业务闭环的子集，不替代完整功能覆盖
- `functional + permission`：按已确认角色矩阵验证允许与拒绝后的业务结果
- `functional + integration`：只断言当前系统可观察的功能结果

## 范围门禁

本流程允许功能、埋点和兼容性矩阵测试用例。埋点和兼容性矩阵必须有当前需求的明确口径与可判定 Oracle，不以 `type=其他` 绕过专属分类。不得产出独立 API、协议、接口字段、安全攻防、性能负载、运维、算法效果或硬件效果测试用例；这些材料仅在支持已允许类型的预期时作为证据。
