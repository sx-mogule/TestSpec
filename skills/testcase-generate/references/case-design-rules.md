## 设计方法

## 创意测试探索

对中等及以上复杂度 TP 触发，简单 TP 跳过。问四个问题：

1. 真实用户最可能的非典型操作是什么？
2. 不同功能模块之间是否有意外交叉影响？
3. 两个操作几乎同时发生会怎样？
4. 除了数值边界，是否存在语义边界？

有价值的场景直接生成用例，标注为 `异常` 或 `边界`；没有好场景时不凑数。在 testcases.json 的 `_context` 中记录：

```json
{
  "creative_scenarios_added": 3,
  "creative_sources": ["用户真实行为", "跨场景组合"]
}
```

## 字段规范

用例至少包含以下八项业务字段及追溯元数据：
- `module`：模块
- `submodule`：子模块
- `test_name`：测试名称，场景部分须简短、直白、见名知意；写法和示例统一见 `../../_testspec-shared/references/naming-contract.md`
- `preconditions`：前置条件，可为空
- `test_data`：测试数据，可为空
- `steps`：按序号编号的操作步骤
- `expected_result`：按序号编号的预期结果
- `priority`：仅允许 `p0` / `p1` / `p2`
- `id`：`{需求名称}_YYYYMMDD{SEQ}`，SEQ 四位递增；仅用于当前变更内追溯，不假设跨变更稳定
- `title`、`feature`：旧格式兼容别名，分别对应 `test_name`、`module`
- `type`：冒烟 / 正向 / 负向 / 边界 / 异常 / 埋点 / 兼容性矩阵 / 其他（后两类须有需求依据和可判定预期）
- `tp_refs`：至少 1 个当前变更内 TP_ID

JSON 字符串中的双引号和反斜杠必须合法转义；推荐用中文引号「」包裹 UI 文案，减少转义风险。

角色、权限或业务状态会影响结果时，前置条件必须明确这些条件。验证输入边界或取消操作时，使用有权编辑的角色及可编辑对象，避免把权限拒绝当成边界拒绝；验证无权限场景时使用合法输入，以隔离拒绝原因。条件须来自已确认需求。

预期结果必须写明**观察对象、状态或变化、可判定依据**，且依据来自已确认需求。缺少会改变通过/失败判断的产品规则时，退回 `test-points` 将该事项列为待澄清项，不编造正式用例；确认后重新生成测试点和用例。

### 四项描述要求

前置条件、测试数据、操作步骤、预期结果统一使用简短、直白、通顺的短句，让测试人员一遍读懂。删掉“请确保”“需要进行”“以便验证”“系统应能够正确地”等套话，不重复字段名称、用例标题或大段背景。不设硬性字数上限，保留执行和判断必需的信息。

| 字段 | 描述要求 |
|---|---|
| 前置条件 | 只写执行前必须具备的角色、权限、对象状态或已完成事项，直接写“已登录”“订单待支付”等状态；不混入操作步骤或预期结果。无必要条件时留空。 |
| 测试数据 | 直接写“字段：值”或明确的数据组合；说明本场景必需的输入、边界值及其单位或格式，不重复前置条件和步骤，不用“有效数据”“测试账号”等泛称代替执行所需的信息。无必要数据时留空。 |
| 操作步骤 | 按序号、按执行顺序，一行写一个动作，用“打开、输入、选择、点击、提交”等动词直接写明动作和对象；引用测试数据时写清对应字段，不省略关键路径，不夹带预期结果或“验证是否正常”等目的说明。 |
| 预期结果 | 按序号，一行写一个可观察结果，直接写明对象及其状态、值、文案或变化，并能对应到相关步骤；不复述操作，不只写“正常”“成功”“符合预期”，不罗列与本用例目标无关的检查。 |

步骤和预期不要求数量相等。多个操作可以对应一个关键结果；逐项核对本用例的主要目标和需求要求的结果，不为凑字数扩句，也不为对齐数量补写无关预期。

以下仅示范表达，具体条件、数据和结果须来自已确认需求：

| 字段 | 冗长或含糊的表达 | 简短清楚的表达 |
|---|---|---|
| 前置条件 | 请确保当前测试账号已经成功登录系统，并且具备订单查看权限 | 账号已登录，有订单查看权限。 |
| 测试数据 | 需要准备一个订单状态为待支付的订单来进行本次测试 | 订单号：DEMO-001；状态：待支付。 |
| 操作步骤 | 测试人员需要进入订单列表页面，然后执行点击目标订单查看详情的操作 | 1、打开订单列表\n2、点击测试数据中的订单。 |
| 预期结果 | 系统应能够正确地展示目标订单的详情，订单状态的展示应符合预期 | 1、显示该订单的详情，状态为「待支付」。 |

## 粒度控制

按互不等价的输入条件、业务分支和 Oracle 拆分用例，不设每个 TP 的固定数量。每条用例只验证一个独立业务意图；仅更换标题或数值且预期相同的内容不得充数。

拆分信号：
- 多个独立验证维度
- 不同验证点失败影响不同
- 需要完全不同的测试数据
- 同一功能的不同验证点有不同优先级

合并信号：
- 验证点高度相关，属于同一原子操作
- 操作步骤完全相同，只是观察角度不同
- 某些验证点必须在同一操作流程中完成
- 拆分会造成用例膨胀且降低执行效率

## 反模式

| 反模式 | 表现 | 正确做法 |
|--------|------|----------|
| 复制粘贴预期 | 所有预期都是"操作成功""正常显示" | 每条预期写清具体状态、数值、文案或系统行为 |
| 过度前置条件 | 前置条件写大量公共环境配置 | 只写与本用例差异相关的条件 |
| 伪边界 | 只是换数值，没有新验证逻辑 | 边界用例必须触发通过/拒绝/提示等不同系统行为 |
| 机械展开 | 每个 TP 都展开相同数量用例 | 按独立业务条件和 Oracle 决定数量 |
| 场景名无信息 | 标题为"测试1""场景A" | 场景名表达具体测试意图 |
| 孤立用例 | `tp_refs` 为空 | 每条用例至少关联 1 个 TP_ID |
