# Review 维度细则

## 使用说明

- 按 R1 → R6 → H1 → H8 顺序执行
- 每个检查项都要输出：`结果`、`关键指标`、`问题列表`
- 问题列表每条必须包含：`severity`、`case_id/TP_ID`、`影响`、`建议`
- 四项描述逐条按 `../../../testcase-generate/references/case-design-rules.md` 检查：能简单就别复杂，只留执行和判定必需的信息；问题按现有维度分级，并进入描述门禁。

### 四项描述门禁

对完整用例集逐条核对四个字段，报告各字段结果；不新增评审维度。确认存在下列问题时，定位到用例和字段，给出原文、原因及可直接替换的短句：

| 字段 | 检查标准 | 常用问题归属 |
|---|---|---|
| 前置条件 | 只写必需角色、权限和初始状态；无套话、重复背景，不夹操作和预期 | H4/H6；无法执行时 R5 |
| 测试数据 | 只列本例必需字段和值；无整套无关配置，准确值、单位、空值和边界保留 | H6；缺必需数据时 R5 |
| 操作步骤 | 按序号用动宾短句写必要路径；无目的修饰、重复操作和无关流程 | H6；无法执行时 R5 |
| 预期结果 | 写清关键对象、变化和值及 Oracle；无套话、重复操作和无关检查，不与步骤机械配数 | H2；偏离主要目标时 H3 |

同义表达、个人用词偏好、字数较长或步骤与预期数量不同，本身都不是违规依据；必须指出具体冗余、歧义或缺项。必要的长文本、精确文案、边界组合和写操作落地检查应保留。

确认的未解决问题统一计入 `description_issue_ids`，每个稳定 issue ID 只计一次；仍按原规则记 S1/S2/S3，不把套话一律升为 S1。存在描述问题即 `review_gate.status=blocked`，包括 S2/S3 和标记为 accepted 的描述问题；复审确认 resolved 后才移出。未完成检查和旧报告的处理、机器字段及通过公式见共享 `output-contracts.md`。

## R1 覆盖度

- 目标：校验 TP 覆盖率
- Strict：按 `tp_refs` 精确计算
- Legacy：按标题前缀推断（低置信度）
- 阈值：覆盖率 ≥ 95% 时 R1 通过，否则 S2。业务分支是否真正可验证，按 H3/H5 裁决。

## R2 命名契约

- 目标：校验 `{模块}_{功能点}_{场景}`
- 校验项：
  - 三段式格式
  - `test_name` 前缀与 `module` 一致，`submodule` 与功能点一致
  - 模块/功能点与 `testpoints.md` 层级一致
  - 按共享 `naming-contract.md` 复核场景短句：主要意图清楚，无套话或流程堆叠，保留区分场景的必要条件，与步骤和预期一致
  - 同一模块/功能点下名称能区分不同意图；不能用“正常场景”“异常测试”或编号代替具体含义
- 名称问题须定位到 `case_id`，给出原名称、问题原因和建议名称；改名只优化表达，不改变用例意图或补造产品结果。不得只按字数判断质量。
- 违规：S2

## R3 优先级分布

- 目标：校验优先级是否有区分
- 关键项：
  - 冒烟必须全部 p0；核对 `regression_tier=Smoke` 的候选也为 p0，`type=冒烟` 同步 Smoke 层级
  - 单一优先级、p0 > 80%、p2 > 50% 视为异常信号
- 异常：S3（分布异常但不一定阻断）

## R4 字段完整性

- 必填：`module`、`submodule`、`test_name`、`preconditions`、`test_data`、`steps`、`expected_result`、`priority`
- 任一缺失：S1

## R5 可执行性最小条件

- `steps` 和 `expected_result` 应具备最小可执行信息
- `steps` 至少包含动作动词（点击/输入/选择/提交等）
- 结合前置条件和测试数据判断动作、对象是否明确，不按字数判断。短句能直接执行即可；“进行操作”等泛称须指出缺少的信息。
- 简化测试数据后，仍须能确定操作对象、输入和判定所需的准确值、单位、边界及组合；缺少执行必需数据时，指出具体缺项，不用“已配置”等泛称掩盖。
- 不满足：S1

## R6 可追溯性

- Strict：
  - 所有用例都要有非空 `tp_refs`
  - `tp_refs` 指向有效 TP_ID
  - 映射率必须 100%
  - 否则 S1
- Legacy：缺少 `tp_refs` 记 S2，并给出升级建议

## H1 冗余检测

- 两阶段：
  1. 相似度筛候选（标题/步骤）
  2. 对比前置条件、数据、步骤和预期，复核是否真重复
- 消费校验结果中的 `review_candidates`，逐对记录差异和保留/合并理由；候选本身不记缺陷。
- 默认结果按组展示。按共享 `execution-efficiency.md` 比较共同内容和全部成员的差异，必要时读取 `duplicate_details` 中的对应相似对；不把组内未相连的两条当作相似对，不按组自动合并。成员或实际差异未核对时不能宣称本项已完成；相同理由可按组说明，无需重复展开全部逐对文字。
- 比较时保留数值、单位、空值、角色、状态和边界位置。需求支持的最小合法值、最大合法值和越界值即使结果相同也不能据此认定重复。
- 只换同一等价类中的普通数值、没有增加必要覆盖时，评估合并；只改标题而内容相同仍需检查。相同 TP 不等于重复，不同 TP 也不保证意图不同。
- 确认重复：S3；不得自动删除或合并候选用例。

## H2 预期结果质量

- 检查模糊表达："正常"、"成功"、"正确" 等无判定标准句式
- 每个关键预期必须包含观察对象、状态或变化，以及来自需求的可判定依据；缺少会改变 Oracle 的规则时不得按通过处理
- 检查预期是否只描述操作完成，却缺少可观察的业务对象、状态变化和判定依据
- 步骤和预期不要求数量相等，也不按预期字数判断；核对需求要求的关键结果是否完整，不给每个点击动作补写无关预期。
- 基于属性的测试应给出每组数据对应的同一业务不变量；变形测试应明确前后结果的比较关系；语法规则分析应给出合法结构的业务结果或非法结构的拒绝依据。缺少可判定 Oracle 或需求依据的用例记 S1
- 模糊表达：S3
- 断言贫乏：S2

## H3 意图一致性

- Strict：按 TP 逐条做 Action/Oracle/Scope 三段评估
- Legacy：标题匹配 fallback，需标注低置信度
- 默认深度：仅高风险 TP 全解释
- 加深深度：所有 TP 全解释
- 意图偏移：S1

### 三段评估定义

- **Action Match**：用例步骤是否真正覆盖了 TP 要求验证的动作或输入条件
- **Oracle Match**：用例预期结果是否覆盖了 TP 的验证目标，而不是只验证表面现象
- **Scope Match**：用例是否引入了 TP 之外的大量验证内容，导致单条用例意图漂移
- **Component Match**：预期是否只断言当前系统可观察行为；不得把调用下游等同于下游副作用完成
- **Scope**：功能、埋点与兼容性矩阵测试点/用例均须有需求证据和可判定 Oracle。埋点核对事件触发、字段及统计口径；兼容性矩阵核对声明的环境组合及逐行预期。缺口或以 `type=其他` 掩盖这两类时记 S1；独立 API、安全、性能及其他未授权类型仍记 S1

### 执行方法

1. 从 `testpoints.md` 读取 TP 的“验证要点”
2. 对照 `tp_refs` 找到对应的用例集合
3. 先看步骤是否落实了 TP 的核心动作或条件
4. 再看预期结果是否给出了可判定的业务结论
   - 每条用例核对主要目标的对应预期。设想操作后页面反馈正确、实际业务状态错误，判断当前步骤和断言能否区分。已确认的主要结果缺失或错误，按本项意图偏移记 S1，即使同一 TP 的另一条用例写对了。
5. 最后检查是否掺入过多旁支验证，导致一条用例同时承担多个不相干目标
6. 核对所引用 TP 的方法集合与 `testcases.json._context.design_methods` 一致。按 `../../../testcase-generate/references/test-design-methods.md` 的“完成判断”查实际覆盖，并在现有“证据/说明”列引用用例、数据、操作和结果。基于属性的测试查适用域与不变量，变形测试查可比前置与关系断言，语法规则分析查结构及业务语义。方法只列标签且未实际落实，按意图偏移记 S1。

### 结论规则

- 三项都成立：判定一致
- `Action Match` 缺失：通常说明步骤没有真正覆盖 TP，要优先修正
- `Oracle Match` 缺失：通常说明预期结果过虚，抓不到真实缺陷
- `Scope Match` 缺失：通常说明 TP 过粗或用例塞入了多个验证意图

## H4 前置条件充分性

- 抽样建议（每模块）：
  - p0 3 条
  - 冒烟 3 条
  - 随机 3 条
- 前置条件需具体、可执行、完整
- 角色、权限或对象状态影响结果时，逐条核对这些条件；边界拒绝须排除权限拒绝，权限拒绝须排除非法输入，取消场景须具备可编辑对象。缺少隔离条件按前置不充分记录。
- 不充分：S2

## H5 风险与边界覆盖

- 按已确认需求确定适用类型和实际覆盖。类型数与分析提供的等价类、边界或状态迁移覆盖率只提示复核。发现具体遗漏后，按业务影响和下列缺口规则分级。
- 输入为可交互 HTML 时，对照 analysis 的 `BTN_ID` 清单逐项核查：已确认的按钮行为须有 TP 与可执行用例，且点击动作和预期结果可追溯；禁用、不可达、未执行和待澄清项须保留状态与原因。遗漏按钮或把未点击项写成已验证，记 S1

### 关键分支缺口

根据当前确认的原始需求或适用项目规范，逐项核对核心路径、明确必测的边界、拒绝路径和状态迁移。原件缺失时说明使用的 canonical 来源。对每一项核对实际成立的前置条件、触发动作和可观察结果。同一目标可由已有用例在等价条件下验证，或由多条用例分别覆盖各独立分支。依赖同一对象的动作与结果须可在同一场景中判定。

- **S1 / H5**：已确认且在范围内的必要路径或条件没有任何用例实际覆盖，导致该规则被实现错误时仍可能通过验收。例：需求明确要求验证合法区间两端，全部 TP 有引用，最大合法值仍无用例。写清该边界及会逃逸的行为，例如系统误拒最大合法值。
- **S1 / H3**：用例或必要 BDD 场景已经执行该路径，但关键预期遗漏、错误或无法判定。伴生 BDD 只核对其应表达的核心路径与关键异常，逐条比较相同条件下约定的业务结果；BDD 与 JSON 冲突时以权威来源裁定。若缺少一整个必要 BDD 场景，按 H5 记录。
- **定位与处置**：在现有需求去向表写清来源位置、遗漏条件或结果、TP/用例 ID 或 feature 路径与场景，以及可能误通过的具体表现。缺少 TP 时引用 REQ 或原文，定位为 `GLOBAL:requirement-coverage` 并指回测试点阶段；已有 TP 但用例或 BDD 不足时交给生成阶段。同一实际缺口以一个 issue ID 进入原 S1 Gate，其他维度或 GR 引用该 ID。
- **S1 / H5**：已有证据表明某项业务在本次承诺验收范围内，但尚未确认的口径会改变关键通过或失败判断。保留原 `Q-xxx`，关联需求或原文位置，说明缺少的确认及影响，创建一个稳定的 S1 issue 归 `prd-analysis`，Gate 保持 blocked。已确认的部分照常评审。确认口径并更新受影响的产物后，由 Review 复核同一 issue。
- 已有等效验证的分支按已覆盖处理。已确认排除的范围记录依据，执行账号、测试数据准备等不影响判定依据的事项记 `dynamic_followups`。来源不足以确认适用范围或影响时，说明限制、请求澄清，并按输入健康规则报告评审完成情况。

## H6 可维护性建议

- 识别可合并冗余、粒度过粗/过细、超长步骤
- 四项描述中的套话、重复背景、无关配置/操作/检查给出可直接替换的精简写法，不转移到其他字段；这类已确认问题纳入描述门禁。具体素材、文案、长文本若参与本例输入或 Oracle 则保留，不按字符数判错。
- 默认 S3

## H7 回归价值评估

  - 抽样：p0、冒烟、风险区域各 3 条（可重叠）
- 反事实提问：
  - 逻辑反转/边界偏移时能否变红
  - 预期结果是否足够精确
  - 是否仅验证“表面响应”而漏检业务副作用
- Oracle 审查：
  - 需求一致性
  - 隐式假设是否可判定
  - 写操作是否有状态落地验证
- 仪式感用例：
  - 1-2 条 -> S3
  - >=3 条 -> S2

### 反事实提问方法

- 如果核心条件判断被写反，这条用例会失败吗
- 如果边界值偏移 1 位，这条用例会失败吗
- 如果状态没有真正落库、只返回了“成功”，这条用例会失败吗
- 如果系统只给出页面提示但业务结果未变化，这条用例会失败吗

### Oracle 审查维度

- 检查 TP 的 `oracle_scope`：direct/contract 可写确定性 oracle；indirect 只能断言本组件产物；out-of-scope 不应生成正式 case
- Legacy import 缺少当前 PRD/TP 追溯时，记录 `GLOBAL:legacy-traceability` S1，不用历史标题猜测 oracle
- Incoming artifact 的 `origin` / `trust` 缺失、为空、枚举未知、组合非法或上下不一致时，记录 `GLOBAL:provenance-unknown` S1；不得按普通 Legacy 降低置信度后放行

- **需求一致性**：预期结果是否有明确需求依据；如果需求没定义，不要把臆测写成正确答案
- **历史一致性**：已有系统行为是否支持这个预期；若是新功能可跳过
- **同类产品一致性**：可作为辅助参考，但不能替代需求依据
- **隐式假设可判定性**：另一个测试人员只看预期结果能否独立判定通过/失败
- **业务副作用完整性**：创建、更新、删除、转账、审批等写操作，不能只看 HTTP/UI 表面响应，必要时要验证数据状态或后续可观察结果

### 仪式感用例识别

- 预期结果过宽，如“页面正常显示”“操作成功”
- 步骤只检查控件存在，不验证业务状态变化
- 前置条件、步骤、预期之间没有明确因果链
- 写操作只验证状态码或提示文案，不验证落库、副作用或后续状态
- 敏感场景未检查越权、数据泄露或关键字段遗漏

## H8 亮点识别

- 标杆用例（可沉淀 testlib）
- 可复用模式（前置条件模板、断言模板、场景模板）
- 输出 1-2 句策略健康度结论
- H8 仅正向反馈，不判失败
