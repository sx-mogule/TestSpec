# Review 维度细则（M / J / D 三层）

14 项检查分三层，每项只有一个判断主体。编号同时是问题标签：问题只在报告的「问题清单」登记一次，矩阵按标签统计。

| 层 | 编号 | 判断主体 | 作用 |
|---|---|---|---|
| M 机器层 | M1–M5 | 脚本 | 评审只引用 `validate_testcases.py`、`validate_context_chain.py` 的结果，不写评语 |
| J 判定力层 | J1–J4 | 评审逐项判断 | 回答“这条规则实现错了，会被拦住吗”，是本评审的主要工作量 |
| D 描述层 | D1–D5 | 评审逐条判断 | D1–D4 即四项描述门禁，D5 为命名与粒度 |

## 分级与 Gate

| 等级 | 含义 |
|---|---|
| S1 | 在已确认规则下错误实现可能通过验收，或用例无法执行、无法判定，或来源被隔离 |
| S2 | 判定能力被削弱但另有用例兜底，或追溯、命名、前置条件会误导执行 |
| S3 | 表达、冗余、分布类问题 |

下表的等级为默认值，依据实际后果判断。

| 是否阻断 Gate | 范围 |
|---|---|
| 阻断 | 任意层未解决的 S1；**J1–J4 任意等级**；**D1–D4 任意等级**（含 accepted） |
| 不阻断 | M 层的 S2/S3、M4、D5、附注 |

“未解决”指状态不是 `resolved`，`open` 与 `accepted` 均计入。

## 两条边界规则

- **J2 与 D4**：影响通过/失败判定的记 J2（别人只看预期无法判定，或错误实现也能通过）；能判定、只是表述冗余的记 D4。
- **J1 与 J2/J3**：没有任何用例或 BDD 实际执行该路径记 J1；执行了但断言或目标偏了记 J2 或 J3。

同一实际缺口只登记一个 issue，不在多个编号下重复登记。

## M 机器层

| 编号 | 名称 | 检查 | 默认等级 |
|---|---|---|---|
| M1 | 覆盖与追溯 | TP 引用覆盖率 ≥ 95%；Strict 下所有用例 `tp_refs` 非空且指向有效 TP | 追溯断链 S1；覆盖率不足 S2；Legacy 缺 `tp_refs` S2 并给升级建议 |
| M2 | 字段与格式 | 八项业务字段齐全；`test_name` 三段式且前缀与 `module`/`submodule` 一致；JSON 合法 | S1（命名格式问题 S2） |
| M3 | 优先级分布 | 冒烟及 `regression_tier=Smoke` 全为 p0；单一优先级、p0 > 80%、p2 > 50% 为异常信号 | S3 |
| M4 | 相似候选 | 脚本 `review_candidates` 的候选组数 | 不单独计问题，交 D5 复核 |
| M5 | 来源与版本 | 来源模式、导入隔离、版本一致、`reviewed_artifacts` 指纹 | Import-Quarantine 记 `GLOBAL:legacy-traceability` S1；Provenance-Unknown 记 `GLOBAL:provenance-unknown` S1 |

M 层数值直接引用脚本输出，不人工重算。脚本 PASS 只说明格式和覆盖率达标，不代表 J 层通过：TP 覆盖率 100% 时仍可能有 J1。

## J 判定力层

### 必测清单（J 层的输入）

先不看 TP，只依据当前需求原文、已确认澄清和适用的 `project-interaction-spec.md`，列出每条规则或分支的“条件 → 可观察结果”：核心路径、明确必测的边界、拒绝路径、状态迁移、写操作的落地结果。原件缺失时说明使用的 canonical 来源。HTML 输入时，analysis 的每个已确认 `BTN_ID` 行为都是必测项。

列完后再对照 TP、用例和 BDD，逐项填入报告的「需求判定力表」。结论只有五种：已拦住 / 漏测（J1）/ 拦不住（J2）/ 待澄清（J4，`Q-xxx`）/ 范围外（写明确认依据）。

标准深度：必测清单列全；反事实检验覆盖 p0、p1、写操作和风险项。`--deep`：反事实检验覆盖全部用例。

### J1 漏测

- 已确认且在范围内的必测项，没有任何用例或 BDD 场景实际执行，导致该规则实现错误时仍可能通过验收。默认 **S1**。
- 例：需求要求验证合法区间两端，全部 TP 都有引用，但最大合法值没有用例。写清该边界及会逃逸的行为，例如“系统误拒最大合法值”。
- 缺少 TP 时引用 REQ 或原文，范围记 `GLOBAL:requirement-coverage`，owner 为 `test-points`；已有 TP 但缺用例或 BDD 时 owner 为 `testcase-generate`。
- 遗漏已确认的 `BTN_ID`，或把未点击项写成已验证，记 J1 S1。
- 缺少一整个必要的伴生 BDD 场景，记 J1。
- 已有等效验证的分支按已覆盖处理；同一目标可由多条用例分别覆盖各独立分支。

### J2 拦不住

- 用例或必要 BDD 场景执行了该路径，但关键预期遗漏、错误、过宽或无法判定，反事实检验下不会变红。默认 **S1**；同一必测项另有用例能拦住时可降为 S2，**仍阻断 Gate**。
- 逐条核对：即使同一 TP 的另一条用例写对了，当前用例的主要目标预期缺失仍要单独登记。
- 反事实提问：
  - 核心条件判断被写反，这条用例会失败吗？
  - 边界值偏移 1 位（`<` 写成 `<=`，按字节而非字符计数），会失败吗？
  - 只返回“成功”、状态没有真正落地，会失败吗？
  - 只给出页面提示、业务结果未变化，会失败吗？
  - 拒绝时有提示、数据却被部分修改，会失败吗？
- Oracle 审查：预期须有需求依据，不把臆测写成正确答案；另一名测试人员只看预期能独立判定通过/失败；创建、更新、删除、审批等写操作要验证数据状态或后续可观察结果，不能只看提示或状态码。同类产品行为只作参考，不替代需求依据。
- 仪式感用例：预期只写“页面正常显示”“操作成功”；只检查控件存在；前置、步骤、预期之间没有因果链；写操作只验证提示文案。
- 生成阶段自检：读 `testcases.json._context.oracle_strength`（规则见 `../../../testcase-generate/references/generation-quality-loop.md`）。Strict 下缺失时记 J2 S2，范围 `GLOBAL:oracle-strength`，owner 为 `testcase-generate`。抽查结论与自检不一致时以本次复核为准，并在判定力表附注差异；自检记录不能代替本项。
- 伴生 BDD 按相同业务条件对照 JSON 的关键结果；两者冲突时回到需求原文裁定，错误一方记 J2。
- 基于属性的测试须给出每组数据对应的同一业务不变量；变形测试须明确前后结果的比较关系；语法规则分析须给出合法结构的业务结果或非法结构的拒绝依据。缺少可判定 Oracle 记 J2。

### J3 偏题

- Strict 下按 TP 逐条做 Action / Oracle / Scope / Component 评估：
  - **Action**：步骤是否真正落实了 TP 要求的动作或输入条件；
  - **Oracle**：预期是否覆盖 TP 的验证目标（不满足时通常同时是 J2，只登记一次）；
  - **Scope**：是否塞入多个不相干的验证意图；
  - **Component**：是否只断言当前系统可观察的行为，不把“调用了下游”等同于下游副作用完成。
- 设计方法落地：所引用 TP 的方法集合须与 `_context.design_methods` 一致，并按 `../../../testcase-generate/references/test-design-methods.md` 的“完成判断”查实际覆盖。方法只贴了标签、没有落实到数据、操作和结果，记 J3 S1。
- 类型范围：有明确依据的埋点、兼容性矩阵按各自 Oracle 核对，缺口或以 `type=其他` 掩盖记 J3 S1；未授权的独立 API、安全、性能等类型记 J3 S1。
- 一条用例承担多个独立意图、但每个意图都能判定时记 J3 S2。
- Legacy 下按标题匹配 fallback，降低置信度并说明。

### J4 口径未定

- 已有证据表明某项业务在本次验收范围内，但尚未确认的口径会改变关键通过/失败判断。保留原 `Q-xxx`，关联需求位置，说明缺少的确认及影响。默认 **S1**，owner 为 `prd-analysis`，Gate 保持 blocked。
- 已确认的部分照常评审。口径确认并更新受影响产物后，由 Review 以同一 issue ID 复核。
- 执行账号、测试数据准备等不影响判定依据的事项记 `dynamic_followups`，不登记 J4。

## D 描述层

D1–D4 对完整用例集逐条检查，不以抽样代替，规则见 `../../../testcase-generate/references/case-design-rules.md`：能简单就别复杂，只留执行和判定必需的信息。确认的问题定位到用例和字段，给出原文、原因和可直接替换的短句。

| 编号 | 字段 | 检查标准 | 默认等级 |
|---|---|---|---|
| D1 | 前置条件 | 只写必需的角色、权限和初始状态；角色、权限或对象状态影响结果时逐条写明；边界拒绝须排除权限拒绝，权限拒绝须使用合法输入，取消场景须具备可编辑对象；无套话、重复背景，不夹操作和预期 | 缺失导致无法执行 S1；隔离不足 S2；套话 S3 |
| D2 | 测试数据 | 只列本例必需的字段和值；准确值、单位、空值、边界和必要组合保留；无整套无关配置，不用“有效数据”等泛称代替必需取值 | 缺少执行必需数据 S1；无关配置 S3 |
| D3 | 操作步骤 | 按序号用动宾短句写必要路径；动作和对象明确，“进行操作”等泛称须指出缺少的信息；无目的修饰、重复操作和无关流程 | 动作或对象不明导致无法执行 S1；多余步骤 S3 |
| D4 | 预期表述 | 写清关键对象、变化和值；无套话、复述操作和无关检查，不与步骤机械配数 | S2 / S3（影响判定的记 J2） |
| D5 | 命名与粒度 | 场景名能表达主要意图、保留区分场景的必要条件，同一功能点下名称能区分不同意图；M4 候选逐组比较全部成员的条件、数据、边界位置和预期后确认是否真重复；粒度过粗或过细 | 名称含糊或与意图不符 S2；确认重复、粒度 S3 |

D 层通用规则：

- 同义表达、个人用词偏好、字数较长或步骤与预期数量不同，本身都不是违规依据；必须指出具体冗余、歧义或缺项。必要的长文本、精确文案、边界组合和写操作落地检查应保留。
- D1–D4 确认的未解决问题，不论 S1/S2/S3，都计入 `description_issue_ids`；`accepted` 也计入，复审确认 `resolved` 后才移出。未完成逐条检查时，记 `GLOBAL:description-review-incomplete` 并保持 blocked。
- D5 复核相似候选时保留数值、单位、空值、角色、状态和边界位置差异；需求支持的最小合法值、最大合法值和越界值即使结果相同也不算重复。只换同一等价类中的普通值、未增加必要覆盖时评估合并；相同 TP 不等于重复。不得自动删除或合并用例。

## 附注：亮点（可选）

有值得沉淀的标杆用例（可进 testlib）或可复用模式（前置条件、断言、场景模板）时列出；不编号、不判失败、不设数量要求。

## 报告映射

- 报告结构使用 `../../../_testspec-shared/templates/review-report-template.md`。
- 每个问题登记为 `- [S1] [open] RV-001 [J1] <范围>`，下附定位、依据、会逃逸的行为或原因、建议和 owner；issue ID 不含等级，等级调整时 ID 不变。
- `## 14 项矩阵` 完整包含 M1–M5、J1–J4、D1–D5，问题数等于问题清单中该编号的登记条数。
