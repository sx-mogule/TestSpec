# BDD 评审流程

需要正式、高可信度或优先列出问题的 BDD 评审时，使用此文件。

## 1. 分类待评审材料

确认：

- 材料类型：场景、特性文件、混合草稿，还是仅有需求
- 用户要求的交付：问题清单、改写、正式报告，还是生成材料
- 判定依据质量：strong、partial 或 weak
- 预期可信度：high、medium 或 low

## 2. 评审意图与追溯

检查：

- 特性或场景意图
- 业务价值是否清楚
- 适用时参与者或角色是否清楚
- 是否链接到已提供的用户故事、规则或需求 ID
- 范围边界

标记：

- 描述测试操作，而非能力的标题
- 创建完整特性文件时缺少或薄弱的业务背景
- 阻碍可靠评审的范围歧义
- 用户要求追溯分析但缺少追溯关系

## 3. 评审场景结构

检查：

- 每条行为路径对应一个场景
- 每个 `When` 只有一个主要事件
- 标题有意义
- 是否重复或重叠
- 分组方式是否有助于可读性，例如按规则、角色或生命周期阶段分组

标记：

- 过载场景
- 应拆分到不同场景或特性中的混杂关注点
- `Test 1`（测试 1）、`Happy path`（成功路径）或 `Check OK`（检查通过）这类场景标题
- 大到难以保持可读性的特性

## 4. 评审路径覆盖

检查：

- 主路径覆盖
- 替代路径覆盖
- 错误或拒绝路径覆盖
- 来源表明相关时的边界、权限和生命周期状态

返回：

- 已覆盖路径
- 缺失路径
- 缺失路径带来的业务风险

## 5. 评审 BDD 质量

检查：

- 业务可读的术语
- 具体示例的质量
- 结果是否可观察
- 上下文是否精简且充分
- 是否避免 UI 脚本
- 是否避免泄漏实现细节

## 6. 只检查明确规定的标准

只根据以下材料检查规范符合性：

- 已提供的需求
- 明确的团队约定
- 明确的元数据规则

不要臆造用户未要求的团队风格。

## 7. 汇总评审发现

使用以下严重度模型：

- `Critical`（严重）：业务行为错误、矛盾、缺失或含糊到无法信任
- `High`（高）：材料很可能误导实现、评审、自动化或签核
- `Medium`（中）：影响范围有限的真实质量问题，例如一个结果较弱，或一个可读但混杂多个路径的场景
- `Low`（低）：措辞、可读性、元数据或低风险清理项

按以下顺序撰写回复：

1. 评审发现
2. 追溯和覆盖说明
3. 辅导或改写建议

如果没有实质性缺陷，应明确说明，然后直接列出剩余缺口或待确认问题。
