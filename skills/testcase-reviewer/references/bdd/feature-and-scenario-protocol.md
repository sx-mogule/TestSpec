# 特性与场景规范

需要特性、场景、标签和路径覆盖的详细结构规则时，使用此文件。

## 特性规则

- 每项能力、一个用户故事规模的行为分组或一组连贯规则使用一个特性文件。
- 特性标题应表达意图，而非测试操作。
- 完整创建或改写特性文件时，只有在来源支持的情况下才加入 `As a / I want / So that`（作为一名……/我想要……/从而……）。
- 特性过大、混合无关逻辑，或涵盖多个没有共同目标的角色时，应拆分。

## 场景规则

- 每条行为路径对应一个场景。
- 每个 `When` 只保留一个主要事件。
- `Given` 只包含理解该行为所需的上下文。
- 在 `Then` 中陈述可观察结果。
- 仅使用 `And` 延续同一阶段。
- 只有在对比能提升清晰度时才使用 `But`。

## 路径覆盖

来源材料支持时，覆盖以下路径类型：

- 主成功路径
- 有效的替代路径
- 错误、拒绝或无效路径
- 适用时的边界、权限或生命周期路径

路径标签如 `@main`、`@alt` 和 `@error` 均为可选。只有项目或来源材料已有标签约定时才使用。

## 命名

标题应表达条件和结果。

推荐：

```text
Scenario: Gold 会员购买符合条件的商品时获得标准折扣
```

避免：

```text
Scenario: 检查折扣
Scenario: 测试 1
Scenario: 成功路径
```

## 标签

仅在以下情况使用标签：

- 项目已有受支持的标签规则
- 来源材料明确提供标签或 ID
- 用户要求保留元数据

不要臆造：

- 需求 ID
- 角色标签
- 优先级标签
- 测试级别标签
- 自动化标签

## `Rule:`

多个场景属于同一业务规则，且规则名称有助于导航时，使用 `Rule:`。

如果 `Rule:` 只增加繁琐度、却没有提升可读性，则避免使用。

## `Background:`

只有在特性文件的每个场景都共享某项上下文时，才使用 `Background:`。

适合的情况：

- 所有场景都处于已认证状态
- 所有场景使用同一账户或目录状态

不适合的情况：

- 大量隐藏的准备工作
- 只有部分场景适用的混合前置条件

## `Scenario Outline`

以下情况使用 `Scenario Outline`：

- 每一行都测试相同的规则结构
- 参数只改变示例，不改变场景含义

以下情况避免使用 `Scenario Outline`：

- 各行代表互不相关的规则
- 各行需要完全不同的预期结果
- 只是为了压缩场景，导致分开书写反而更清晰

## 示例设计

- 优先使用真实合理的示例，而非占位符。
- 阈值重要时，使用边界值。
- 生命周期状态会改变结果时，使用能体现状态差异的示例。
- 术语应符合业务领域并保持一致。
