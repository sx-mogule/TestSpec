# BDD 质量规则

此文件提供详细的评审标准、改写方法和反模式修正方式。

## 核心检查清单

条件允许时，确认以下各项：

- 业务规则清晰
- 场景描述一条行为路径
- `Given`、`When` 和 `Then` 的意图明确
- 步骤使用业务层面的描述
- 结果可从系统外部观察
- 措辞具体且与业务领域相关
- 利益相关方能够理解场景
- 开发人员能够据此实现预期行为
- 测试人员无需猜测即可验证

## 推荐模式

### 具体示例

推荐：

```gherkin
Given 一位订阅有效的 Gold 会员
When 该会员购买符合条件的商品
Then 结账总额包含 Gold 会员的标准折扣
```

避免：

```gherkin
Given 一位 <customerType>
When 用户购买一件 <item>
Then 系统处理该折扣
```

### 单一职责场景

每个场景只关注一条规则分支或一种结果。

### 面向业务的语言

使用利益相关方熟悉的术语。除非技术名词属于业务领域，否则应将其删除。

### 可观察结果

写出用户、测试人员或外部观察者可以直接验证的结果。

### 精简的 `Given`

只保留理解操作及其结果所需的上下文。

## 常见反模式

### 伪装成 BDD 的 UI 脚本

避免：

```gherkin
Given 我点击登录按钮
And 我输入用户名
And 我点击提交
```

### 多个重要事件

避免在一个场景中包含多个会改变场景目的的用户操作。

### 在单个场景内分支

避免在同一场景中混合不同的替代结果，或使用条件式表述。

### 含糊的结果

避免：

```gherkin
Then 它可以正常工作
Then 请求成功
Then 结果正确
```

### 不可见的结果

除非用户明确要求内部验证，否则不要将日志、内部表、选择器或实现细节作为主要结果。

### 笼统的数据

如果具体示例能更清楚地说明规则，就不要使用占位符。

### 滥用 `Background:`

不要将大量隐藏的前置准备放入 `Background:`。

## 修正方式

直接采用以下修正：

- UI 脚本式步骤 → 改写为业务语言
- 含糊的 `Then` → 替换为可观察结果
- 过载场景 → 拆分成多个场景
- 笼统标题 → 按条件和结果重新命名
- 缺少路径覆盖 → 增加来源支持的主路径、替代路径或错误场景
- 示例数据薄弱 → 替换为真实合理的数据

## 可信度规则

即使无法判断正确性，仍可评估质量问题。

判定依据较弱时：

- 评审结构、清晰度和 BDD 质量
- 降低可信度
- 避免断言场景在行为上正确
