# 接收与决策流程

请求含糊、混合多种目标或信息不足时，使用此文件。

## 1. 确定交付内容

选择主要交付内容：

- 仅评审 → `review`
- 仅改进材料 → `rewrite`
- 根据需求新建材料 → `generate`
- 评审并改进材料 → `hybrid`
- 正式评分卡或执行摘要 → `review` 加正式报告契约

## 2. 评定判定依据

使用以下充分程度模型：

- `strong`：已提供明确业务规则、验收标准或权威需求
- `partial`：已有部分需求，但仍缺少重要分支或业务术语定义
- `weak`：只有原始场景文字、特性文件文字或笼统备注

## 3. 设置可信度

使用以下可信度模型：

- `high`：判定依据充分且歧义少
- `medium`：判定依据部分充分，或存在有限歧义
- `low`：判定依据薄弱、输入互相冲突或存在重大歧义

判定依据薄弱时，不要报告 `high` 可信度。

## 4. 决定继续或暂停

以下情况可直接继续，不必先提阻塞性问题：

- 用户要求结构评审
- 任务主要关注 BDD 质量
- 可在明确标注假设的前提下完成有用的改写
- 即使只能部分生成，结果仍有价值

仅在以下情况暂停并询问：

- 错误假设会实质性改变行为
- 用户期待的正确性结论缺乏依据
- 存在多个同等可能但互不相容的解释

## 5. 选择输出深度

以下情况采用快速评审：

- 一个场景
- 一个简短特性
- 轻量辅导

以下情况采用正式评审：

- 按严重度排序的报告
- 评分卡
- 追溯分析
- 执行摘要
- 发布或驳回材料的决策

## 6. 薄弱输入的默认处理

判定依据薄弱时：

- 正常评审结构和质量
- 明确降低可信度
- 避免断言行为覆盖完整
- 列出无法判定的事项或缺失规则

## 7. 推荐表述

可使用以下表述：

- `Oracle sufficiency: partial`（判定依据充分程度：部分充分）
- `Confidence: low`（可信度：低），因为验收标准没有定义拒绝路径。
- 可以改进材料的结构，但无法根据所提供的来源确认其行为是否正确。
