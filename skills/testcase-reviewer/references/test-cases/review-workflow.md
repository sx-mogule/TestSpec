# 评审流程参考

## 用途

需要采用完整结构化评审方法，而非轻量点评时，使用此参考流程。

## 步骤 1：需求分析与追溯

1. 收集所有可用的判定依据文档。
2. 提取可识别的需求单元，例如需求 ID、用例、验收标准或业务规则。
3. 将每项需求标记为：
   1. 清晰且可测试
   2. 含糊
   3. 不完整
4. 记录阻碍精确测试的缺失细节。
5. 建立需求到测试的映射。
6. 标记没有关联测试用例的需求。

## 步骤 2：测试套件结构评审

1. 仅在存在套件或文件夹结构时执行本步骤。
2. 检查该层级是否便于快速查找测试。
3. 顶层优先按组件或可部署区域分组。
4. 中间层优先按测试级别或测试类型分组。
5. 底层优先按判定依据来源或需求单元（例如用例）分组。
6. 若底层套件超过约 20 条用例，标记为可考虑拆分。
7. 标记容易在多个套件中产生重复用例的结构。
8. 检查该结构是否支持映射到实现类，且映射清晰易读。

## 步骤 3：覆盖分析

1. 确认每项需求至少有一条测试覆盖。
2. 确认已覆盖以下功能路径：
   1. MSS
   2. EXT
   3. ERR
3. 确认覆盖了所有有意义的业务规则结果。
4. 若存在多种计算类别，确认每种类别都有独立测试。
5. 评估是否采用了恰当的设计方法：
   1. 用等价类划分覆盖有代表性的输入类别
   2. 用边界值分析检查边缘值和限制
   3. 用决策表覆盖业务规则组合
   4. 用状态转换测试覆盖状态变化
   5. 用用例测试覆盖参与者驱动的流程
6. 分别标记未覆盖场景和重复场景。

## 步骤 4：技术正确性验证

1. 验证测试判定依据是否恰当。
2. 优先使用已批准的需求、验收标准、分析文档、手册或利益相关方确认的行为。
3. 将基于代码得出的判定依据标记为评审风险。
4. 检查前置条件是否：
   1. 确保所需系统可用
   2. 确保所需数据存在
   3. 建立所需用户角色或系统状态
5. 检查操作步骤是否：
   1. 可执行
   2. 具有确定性
   3. 不包含隐含假设
6. 检查预期结果是否：
   1. 具体
   2. 可衡量
   3. 可验证
   4. 与可观察结果关联
7. 检查测试数据是否：
   1. 真实
   2. 有代表性
   3. 考虑了边界
   4. 能覆盖反向路径

## 步骤 5：规范符合性

1. 检查标题质量。
2. 检查必填字段。
3. 检查追溯标记。
4. 检查测试分类，例如 MSS、EXT 或 ERR。
5. 如果本地模板要求编号或字母标注，检查前置条件和步骤是否遵循。
6. 检查项目是否使用优先级或测试级别，并核对其设置。
7. 标记 `test 1`（测试 1）、`OK`（通过）或 `error case`（错误场景）这类笼统标题。

## 步骤 6：辅导与评估

1. 总结优点，但不要掩盖严重缺口。
2. 将重复出现的问题归纳为技能提升主题。
3. 给出 3 至 5 条具体改进建议。
4. 按业务影响排序建议。
5. 仅在用户要求评分或工作流要求时生成评分矩阵。
6. 最后列出让测试集达到可评审状态所需的下一步行动。
