# 测试套件规范参考

## 1. 测试套件的用途

1. 将套件视为便于查找测试并减少重复的逻辑容器。
2. 优先采用能让人从层级位置直接看出测试目的的结构。

## 2. 高层结构

1. 条件允许时，最高层按组件、子系统或可部署区域分组。
2. 常见示例：
   1. Web 应用
   2. API 服务
   3. 批处理任务
   4. 路由平台

## 3. 中间层结构

1. 适用时，中间层按测试级别或测试类型分组。
2. 常见示例：
   1. 集成测试
   2. 契约测试
   3. 服务测试
   4. 系统测试
   5. 端到端测试（E2E）
   6. UI 测试

## 4. 底层结构

1. 底层按判定依据来源或需求单元分组。
2. 常见示例：
   1. 用例
   2. 数据流
   3. 验收标准分组
   4. 操作指南
3. 只有测试类型不同时，才在多个分支复用同一个需求单元名称。

## 5. 拆分规则

1. 底层套件难以搜索、评审或维护时应拆分。
2. 可将约 20 条用例作为讨论拆分的实用阈值。
3. 按有意义的行为、输入类型或流程变体拆分，不要只按编号随意拆分。

## 6. 重复规则

1. 不要为了表面上的追溯效果，将同一逻辑路径放进多个套件。
2. 尽可能利用层级结构支持需求映射。
3. 如果正常运行中同一路径被重复执行，且无合理的测试类型差异，则标记为重复场景。

## 7. 评审问题

1. 评审人员能否通过层级和标题快速找到某条测试？
2. 不打开每条用例，能否从结构看出已覆盖的需求？
3. 每个底层套件能否清晰映射到一个实现类或自动化单元？
4. 套件是否过宽、过于扁平或重复过多？
