# 迷你评审报告示例

需要参考完整评审输出示例时，使用此参考资料。以下示例按质量阶梯排列，从很差到优秀。

## 目录

1. 很差的报告：含糊且无结构
2. 薄弱的报告：列出问题但没有依据
3. 中等的报告：有用但不完整
4. 良好的报告：发现清楚、行动明确
5. 良好的报告：侧重辅导
6. 很好的报告：可追溯且可执行
7. 很好的报告：高质量套件评审
8. 优秀的报告：侧重签核

## 1. 很差的报告：含糊且无结构

### 输入情况

- 部分需求来源可用
- 提供了两条登录测试用例草稿

### 薄弱评审报告

```text
这些测试大体没问题，但还需要修改。增加更多细节，也许再增加一些反向测试。
```

### 薄弱之处

- 没有结构
- 没有指出具体需求或测试用例
- 没有严重度或优先级
- 没有可执行的下一步

### 改进方向

- 指出确切缺失的场景
- 说明哪些预期结果无法验证
- 按严重度排列问题

## 2. 薄弱的报告：列出问题但没有依据

### 输入情况

- 密码重置 UAT 场景
- 已知过期令牌处理问题

### 薄弱评审报告

```text
执行摘要：
该套件在覆盖和质量方面存在问题。

问题：
- 标题不好
- 前置条件薄弱
- 反向测试不充分
```

### 薄弱之处

- 仍然过于笼统
- 没有引用具体示例
- 没有将评审发现关联到需求或签核风险

### 改进方向

- 指出受影响的场景
- 说明哪些需求或验收标准覆盖不足
- 给出具体修正建议

## 3. 中等的报告：有用但不完整

### 输入情况

- 包含 5 条手工测试用例的转账功能
- 可获得需求 ID

### 中等评审报告

```text
执行摘要：
草稿覆盖了主要转账路径，但还不足以支持签核。

评审发现：
- High：REQ-05 缺少余额不足时的反向路径覆盖。
- Medium：若干预期结果过于笼统。
- Low：部分标题可以更具体。

建议：
- 增加反向测试。
- 改进标题。
- 为预期结果补充更多细节。
```

### 仍属中等的原因

- 有严重度
- 提供了一些具体依据
- 仍缺少详细追溯信息和完整输出结构

### 改进方向

- 加入需求到测试的映射摘要
- 区分必须修复的问题和辅导建议
- 说明“补充更多细节”应具体到哪些可观察结果

## 4. 良好的报告：发现清楚、行动明确

### 输入情况

- 结账运费规则场景
- 有限额需求和三条测试草稿

### 良好评审报告

```text
执行摘要：
当前用例集体现了良好的边界意识，但还不够完整，暂时不能签核。

覆盖分析：
- REQ-44 部分覆盖。
- 已有 49.99 EUR 的用例。
- 尚缺阈值和高于阈值的场景。

技术正确性：
- 预期结果可观察，且关注 UI。
- 前置条件足以支持手工执行。

行动计划：
1. 增加 50.00 EUR 的用例。
2. 增加 50.01 EUR 的用例。
3. 在同一套件中将三条用例标记为一组边界测试。
```

### 良好之处

- 结构清晰
- 指出了确切缺失的场景
- 给出了具体的下一步

### 可改进之处

- 添加严重度标签
- 说明套件命名是否仍然合适

## 5. 良好的报告：侧重辅导

### 输入情况

- 初级测试人员提交了忠诚度折扣用例
- 决策逻辑包含顾客状态与优惠券交互

### 良好评审报告

```text
执行摘要：
分析人员写出了清晰的成功路径场景，并使用了真实合理的数据，但对基于决策的覆盖考虑不足。

已观察到的优点：
- 标题易读。
- 预期价格可通过数值验证。

提升空间：
- 决策逻辑仅得到部分覆盖。
- 缺少优惠券覆盖规则。

辅导建议：
- 用包含顾客状态和优惠券是否存在两项条件的小型决策表，取代临时挑选用例的做法。
```

### 良好之处

- 反馈平衡
- 适合用于辅导
- 指出了适当的测试设计方法

### 可改进之处

- 添加明确的需求 ID
- 将辅导意见转化为具体缺失用例

## 6. 很好的报告：可追溯且可执行

### 输入情况

- ATM 取款套件
- 已提供需求和每日限额规则

### 很好的评审报告

```text
执行摘要：
总体评分：7/10。套件清晰且可执行，但由于每日取款限额的边界覆盖不完整，REQ-12 仍只得到部分覆盖。

需求分析与追溯：
- REQ-12 -> 由累计取款状态为 550 EUR 的 TC04 覆盖
- 缺少关联用例，未覆盖恰好达到限额和略低于限额的行为

覆盖分析：
- MSS 覆盖：已有
- ERR 覆盖：部分已有
- 边界覆盖：不足

技术正确性：
- 前置条件具体且可复现。
- 预期结果正确断言了拒绝提示和余额未变。

行动计划：
1. 增加 TC05，验证累计金额恰好为 500 EUR。
2. 增加 TC06，验证最后一次取款前累计金额为 499 EUR。
3. 保留 TC04 作为超出限额时的拒绝用例。
```

### 优秀之处

- 结论关联到需求 ID
- 指出了确切缺失的边界
- 修正计划清晰

## 7. 很好的报告：高质量套件评审

### 输入情况

- 一个底层套件包含 34 条密码重置测试
- 混合了手工和面向自动化的草稿

### 很好的评审报告

```text
执行摘要：
当前套件结构已成为维护风险。一个底层分组包含了过多行为，并可能导致重复路径执行。

套件结构评审：
- 当前套件超过了便于维护的实际阈值。
- 令牌过期、令牌复用、用户不存在和限流场景混在一起，没有合理的子分组。

建议：
- 将套件拆分为：
  - 令牌有效性
  - 用户身份与账户状态
  - 防滥用和限流

风险：
- 如果不拆分，后续迭代很可能会重复新增用例，且追溯关系会逐渐偏移。
```

### 优秀之处

- 结构问题诊断清楚
- 依据可维护性风险
- 给出了合理的拆分方案

## 8. 优秀的报告：侧重签核

### 输入情况

- 支付授权流程
- 3-D Secure 验收标准包含超时规则
- 草稿混合了 MSS 和 ERR

### 优秀评审报告

```text
执行摘要：
总体评分：8/10。草稿接近可签核质量，追溯和可观察性都很强；但 AC-21.4 仍缺少与超时规则配对的 MSS 边界场景，用于验证超时前一刻确认的行为。

需求分析与追溯：
- UC21 TC11 部分覆盖 AC-21.4。
- 已覆盖 5 分钟后的过期路径。
- 缺少 5 分钟前一刻的成功路径。

覆盖分析：
- MSS：部分覆盖
- ERR：超时情况已完整覆盖
- 状态/时间边界：不完整

技术正确性：
- 前置条件定义了网关可用、挑战开始时间和卡片能力。
- 预期结果覆盖 UI 提示、订单状态、购物篮保留和审计记录。

规范符合性：
- 标题质量良好。
- 前置条件和预期结果均已编号且可复现。

行动计划：
1. 增加一条 MSS 时间边界用例，在 4 分 59 秒时确认。
2. 保留 UC21 TC11 作为超时 ERR 用例。
3. 将两条用例标记为 AC-21.4 的配对验收标准用例集。
```

### 优秀之处

- 聚焦签核
- 信息足够完整，可立即执行
- 在一份精炼报告中结合追溯、覆盖、正确性和规范符合性
