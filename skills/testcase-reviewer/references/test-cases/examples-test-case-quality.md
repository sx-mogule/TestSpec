# 测试用例质量示例

需要判断用例质量、解释评审发现或辅导测试作者时，使用此参考资料。以下示例按质量阶梯排列，从很差到优秀。

## 1. 很差的示例：没有上下文

### 草稿

- 标题：`测试登录`
- 前置条件：无
- 步骤：`登录`
- 预期结果：`可以正常工作`

### 问题所在

- 没有需求或套件上下文
- 没有准备系统状态
- 步骤没有可执行的细节
- 没有可观察的预期结果
- 无法安全地追溯或自动化

### 改进方向

- 指明参与者、输入及预期 UI 或 API 响应
- 说明执行前的登录状态
- 使用包含路径分类的描述性标题

## 2. 很差的示例：笼统的错误用例

### 草稿

- 标题：`错误测试`
- 前置条件：`系统已启动`
- 步骤：
  - `输入错误的内容`
- 预期结果：
  - `报错`

### 问题所在

- 未定义无效输入
- 错误结果过于含糊
- 没有业务规则或判定依据引用
- 无法复现

### 改进方向

- 明确指出无效输入
- 明确指出预期的校验消息或拒绝码
- 将用例关联到需求或验收标准

## 3. 薄弱的示例：判定依据照搬代码

### 草稿

- 标题：`TC03 计算折扣`
- 前置条件：
  - `服务已部署`
- 步骤：
  - `发送 vip=true 的折扣请求`
- 预期结果：
  - `折扣为 12，因为服务现在就是这样返回的`

### 问题所在

- 预期结果基于当前实现行为
- 没有已批准的业务判定依据
- 很可能会出现“测试通过但行为错误”的情况

### 改进方向

- 引用定价规则或验收标准
- 说明折扣应为 12 的依据
- 如果规则取决于顾客状态，应添加边界和非 VIP 对照场景

## 4. 薄弱的示例：缺少反向覆盖

### 草稿

- 标题：`UC05 TC01: MSS - 转账成功`
- 前置条件：
  - `用户已登录`
  - `转出账户有 500 EUR`
- 步骤：
  - `向目标账户转账 100 EUR`
- 预期结果：
  - `转账成功`
  - `余额已更新`

### 薄弱之处

- 仅覆盖了成功路径
- 未测试余额不足、账户冻结和金额无效的情况
- 预期结果仍然过于笼统

### 改进方向

- 增加 ERR 和 EXT 场景
- 明确具体的转出和转入余额
- 指明转账状态或确认提示

## 5. 薄弱的示例：前置条件不足

### 草稿

- 标题：`UC09 TC02: ERR - 密码重置失败`
- 前置条件：
  - `用户存在`
- 步骤：
  - `重置密码`
- 预期结果：
  - `重置被拒绝`

### 薄弱之处

- 不清楚拒绝原因
- 缺少过期令牌或已使用令牌等触发条件
- 缺少可观察结果

### 改进方向

- 定义确切的失败条件
- 描述请求渠道和令牌状态
- 断言具体错误提示以及密码状态未变化

## 6. 中等的示例：描述清楚但不完整

### 草稿

- 标题：`UC12 TC03: ERR - 取款金额超出每日限额时拒绝取款`
- 前置条件：
  - `客户已通过身份验证`
  - `客户当日累计取款金额为 450 EUR`
  - `每日限额为 500 EUR`
- 步骤：
  - `请求取款 100 EUR`
- 预期结果：
  - `取款被拒绝`

### 优点

- 标题明确
- 数值合理
- 错误条件清楚

### 缺失项

- 没有明确的判定依据引用
- 没有预期的拒绝码或提示
- 没有断言余额及审计记录保持正确

### 改进方向

- 将用例关联到取款限额需求
- 断言余额未变、显示拒绝原因，并在有要求时记录事件

## 7. 良好的示例：清晰的手工用例

### 草稿

- 标题：`UC12 TC04: ERR - 取款金额超出每日限额时拒绝取款`
- 前置条件：
  - `A. 客户已在 ATM 会话中通过身份验证`
  - `B. 客户账户余额为 1200 EUR`
  - `C. 客户当天已取款 450 EUR`
  - `D. 每日取款限额为 500 EUR`
- 步骤：
  - `1. 输入取款金额 100 EUR`
  - `2. 确认取款请求`
- 预期结果：
  - `1. ATM 拒绝交易`
  - `2. 显示提示“已超过每日取款限额”`
  - `3. 账户余额仍为 1200 EUR`

### 良好之处

- 准备充分
- 步骤可执行
- 预期结果可观察
- 易于评审，也便于后续自动化

### 可改进之处

- 添加需求 ID
- 项目使用测试级别或优先级时，将其补充进来

## 8. 良好的示例：聚焦边界的用例

### 草稿

- 标题：`REQ-44 TC06: MSS - 购物篮总额为 49.99 EUR 时仍可提供高级配送`
- 前置条件：
  - `A. 高级配送的门槛金额为 50.00 EUR`
  - `B. 客户购物篮中有有效且有库存的商品，合计 49.99 EUR`
- 步骤：
  - `1. 打开结账页面`
- 预期结果：
  - `1. 不提供高级配送`
  - `2. 提供标准配送`

### 良好之处

- 边界条件清楚
- 数值精确
- 预期行为可测试

### 可改进之处

- 配套增加 50.00 EUR 和 50.01 EUR 的相邻边界用例
- 如果需求有歧义，引用原文

## 9. 很好的示例：充分覆盖业务规则

### 草稿

- 标题：`REQ-18 TC08: EXT - 顾客为 Gold 且未使用优惠券时应用忠诚度折扣`
- 前置条件：
  - `A. 定价规则 REQ-18 规定：无优惠券覆盖时，Gold 顾客享有 10% 的忠诚度折扣`
  - `B. 顾客状态为 Gold`
  - `C. 购物篮小计为 200 EUR`
  - `D. 未使用优惠券`
- 步骤：
  - `1. 打开订单摘要`
  - `2. 完成定价`
- 预期结果：
  - `1. 显示忠诚度折扣明细`
  - `2. 折扣金额为 20 EUR`
  - `3. 最终价格为 180 EUR`
  - `4. 不显示优惠券折扣明细`

### 很好之处

- 判定依据明确
- 业务条件清楚
- 有数值断言
- 同时验证已应用和未应用的行为

## 10. 优秀的示例：已达到可评审状态的用例

### 草稿

- 标题：`UC21 TC11: ERR - 3-D Secure 挑战在确认前过期时拒绝支付授权`
- 前置条件：
  - `A. UC21 和 AC-21.4 规定：未在 5 分钟内确认 3-D Secure 挑战时，支付必须失败`
  - `B. 客户已通过身份验证，且购物篮中有商品`
  - `C. 支付网关沙箱可用`
  - `D. 测试卡支持 3-D Secure 挑战流程`
  - `E. 挑战于 10:00 开始，至 10:05 前都未提交确认`
- 步骤：
  - `1. 使用 3-D Secure 测试卡提交订单`
  - `2. 等待挑战过期`
  - `3. 返回商家网站`
- 预期结果：
  - `1. 支付状态为 Rejected`
  - `2. 未创建订单`
  - `3. 客户看到提示“身份验证超时，请重试。”`
  - `4. 购物篮内容保持不变`
  - `5. 审计记录中记录了超时拒绝原因`

### 优秀之处

- 判定依据和时间规则明确
- 系统依赖符合实际
- 状态路径精确
- UI、业务状态和审计行为均有清晰可观察结果
- 已可用于评审、执行及自动化映射
