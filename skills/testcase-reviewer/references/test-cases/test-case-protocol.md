# 测试用例规范参考

## 1. 核心原则

1. 将测试用例视为针对一个测试目标，描述前置条件、输入、操作和预期结果的规格说明。

## 2. 判定依据规则

1. 以已批准的需求、验收标准、分析文档、用户手册或利益相关方确认的规则为判定依据。
2. 不要将实现代码作为主要判定依据。
3. 如果测试似乎依据实现而非业务行为编写，应指出“测试通过但行为仍可能错误”的风险。

## 3. 覆盖规则

1. 未指定较低的目标覆盖范围时，应覆盖全部有意义的功能结果。
2. 如果多个路径都可能产生相同结果类别，不要每类只测一个真值、一个假值或一个未执行用例就停止。
3. 计算或分类中每种有意义的结果类别都应单独测试。

## 4. 测试设计方法要求

1. 对预期行为相似的输入类别使用等价类划分。
2. 对数字、日期、长度、数量或阈值限制使用边界值分析。
3. 对相互作用的业务规则和条件使用决策表测试。
4. 对包含状态、守卫条件和生命周期变化的工作流使用状态转换测试。
5. 不要将探索式测试、检查清单测试或错误猜测作为正式设计测试用例的主要依据。

## 5. 标题规则

1. 标题必须有描述性。
2. 标题应包含：
   1. 可用时，注明需求或套件上下文
   2. 顺序标识
   3. 测试类型，例如 MSS、EXT 或 ERR
   4. 对应具体行为的文字
3. 推荐标题示例：
   1. `UC04 TC01: MSS - 居住地位于 Flanders（佛兰德斯）时，affiliability（隶属资格）为 OK`
4. 以下标题不合格：
   1. `test 1`
   2. `OK`
   3. `error test`（错误测试）

## 6. 前置条件

1. 定义首次操作开始前的系统状态。
2. 按需包含数据准备、用户角色、服务状态或输入材料。
3. 逻辑上合理时，以下任一写法均可接受：
   1. 将准备事项作为前置条件
   2. 将准备事项作为第一步操作
4. 优先使用明确的编号或字母标识，便于映射到实现。

## 7. 操作

1. 将操作写成清晰、可执行的步骤。
2. 根据测试类型使用面向用户或面向系统的描述。
3. 执行顺序重要时，步骤应编号。

## 8. 预期结果

1. 将预期结果写成可观察的结果。
2. 可使用以下断言目标：
   1. UI 提示
   2. API 响应内容
   3. 数据库记录
   4. 文件移动
   5. 发出的事件
   6. 与行为相关的日志条目
3. 不接受主观或无法验证的预期结果。

## 9. 优先级

1. 检查项目是否使用测试级别或优先级。
2. 若项目采用五级尺度，按以下方式理解：
   1. 级别 1：MSS 和最常见路径
   2. 级别 2：重要扩展路径及尚未覆盖的路径
   3. 级别 3：其他组合和数据变体
   4. 级别 4：侧重循环或价值较低的变体
   5. 级别 5：可忽略或延期的测试
3. 若简单用例的优先级高于核心业务路径，标记优先级不一致。
